# Manual traffic investigation guide

This document defines **process**, not the answer. Do not put guessed incident details here before they are observed through the application.

## Purpose
The repository asks the candidate to use the completed interface to find the compromised machine, identify where the suspicious activity started, link to that evidence in the UI, and mention what was ruled out.

The investigation is part of the product acceptance test: if the UI cannot support this workflow, improve the UI before trying to work around it elsewhere.

## Evidence boundary
During T8, allowed evidence sources are:
- the running frontend;
- normal data the frontend obtains through its BFF/API calls;
- URLs generated by the frontend;
- the public repository `README.md` and already-established API contract notes.

During T8, do **not** inspect:
- backend source code;
- backend tests;
- `backend/src/capture_api/world/**`;
- incident/world generators;
- fixtures/samples that could encode the answer;
- source-code searches for suspected host/domain/IP values.

Do not use code as a second source to "confirm" a UI-derived guess. The README explicitly requires the answer to come from the interface.

## Investigation mindset
Do not equate one unusual event with compromise. The dataset intentionally contains suspicious-looking benign traffic.

Prefer a chain of evidence:

```text
anomaly
  -> candidate host
  -> chronological follow-up
  -> cross-protocol or repeated behavior
  -> pivot around the same host
  -> alternative explanations considered
  -> reproducible evidence
```

Useful patterns to inspect may include, without treating any one as proof:
- a host changing behavior at a particular time;
- unusual outbound destinations;
- repeated/periodic connections;
- DNS followed by related network traffic;
- bursts or regular beacons;
- protocol/port combinations that are unusual for that host;
- multiple independent observations that point to the same machine.

## Recommended workflow

### 1. Establish baseline
Start with a broad but manageable time window and inspect normal traffic shape.
Understand common hosts, common protocols, and recurring destinations before labeling anomalies.

### 2. Form a candidate
When something looks abnormal, record why it deserves inspection. Do not label it compromised yet.

### 3. Pivot by host
Use source/destination pivots to inspect other sessions involving the same machine.
Preserve a reproducible URL for the candidate search.

### 4. Build chronology
Sort/inspect timestamps so the sequence is understandable.
Look for what immediately preceded and followed the suspicious event.

### 5. Correlate
Look across sessions/protocols for supporting behavior. A single odd DNS query or port is weak evidence; a repeatable sequence can be much stronger.

### 6. Challenge the hypothesis
Try to rule the candidate out. Compare with other hosts or benign patterns. Record a false lead when there is a concrete reason it was rejected.

### 7. Identify the earliest defensible point
The README asks where it started. Capture the earliest suspicious timestamp/session that the UI evidence can support, not merely the most dramatic later event.

### 8. Preserve evidence
Before writing README, save:
- compromised host identifier;
- approximate earliest suspicious timestamp / starting point;
- reproducible search URL;
- at least one stable `/sessions/{id}` URL;
- short correlation reasoning;
- at least one false lead and why it was ruled out.

## README conversion
Keep final README prose concise. The investigation log can be more detailed, but the submitted README should usually contain:
- the compromised host;
- where/when the suspicious chain begins;
- one hunt/search link;
- one representative session link;
- 2–5 sentences on how the evidence correlated;
- one sentence on a plausible false lead that was ruled out.

Do not overstate certainty beyond what the UI evidence supports.

### Uncertainties and limitations
- The UI evidence strongly supports `ws-hb-009` as compromised, but it does not expose an asset-to-user directory or endpoint execution telemetry. The association between the phishing recipient and that workstation, and execution of the attachment, remain timeline-based inferences rather than directly observed facts.
- The first observed TLS callback is not treated as the start of compromise. The SMTP delivery is the earliest suspicious event in the correlated timeline, while the 06:11:38 DNS lookup is the earliest suspicious event directly emitted by the host.
- PCAP was already expired for the inspected historical sessions, so the conclusion uses decoded session fields, detections, risk reasons, and chronology visible in the application.
